# Lesson log

Learnings captured while building OpenPath. One entry per lesson, newest last. Workers: when you learn something reusable during a ticket, append it here in the same format.

## 2026-07-31, backlog v2 build (tickets 01 to 18)

1. **Write the architecture doc before the first build ticket.** CONTEXT.md plus docs/architecture.md let 15 build tickets run against one source of truth. Every worker brief started with "read these two files"; drift stayed near zero across 8 different agent runs.
2. **A domain language file prevents naming rot.** "Opportunity, not job", "Dream is a flag, not a status", "one Copilot, not assistants" held across the whole codebase because CONTEXT.md fixed the words on day one.
3. **The trust boundary is a design rule, not a feature.** "AI drafts, the user accepts, edits, or dismisses" decided dozens of small UI questions without discussion. One absolute rule beats many local judgments.
4. **Ticket briefs should state what the next ticket will deepen.** Ticket 06 built tab scaffolds and named which tickets (07, 08, 10) would fill them. No tab was ever blank and no ticket rebuilt another's structure.
5. **Seed data is product design.** The persona (Mai Tran) with coherent dates, one low-credibility posting, one stale opportunity, and one raw unanalyzed opportunity made every AI behavior demonstrable. Generic seed data would have hidden half the features.
6. **Health check a flaky worker with a trivial prompt before sending a big brief.** `droid exec --auto low "Reply with: ready"` separates service outage from a bad brief in seconds. Droid died twice mid-ticket today; both times the check confirmed outage and the work was handed to a fallback agent that finished from the uncommitted state instead of rebuilding.
7. **Uncommitted work from a dead agent is usually salvageable.** Both droid failures happened during final verification, after the build was essentially done. The recovery brief was "review against the original brief, finish, verify, commit", which cost a fraction of a rebuild.
8. **Vercel CLI direct deploys can silently drop tracked files.** `vercel deploy --prod` failed with module-not-found for a file that exists, is tracked, and is pushed; `--force --archive=tgz` did not fix it. The reliable path: `vercel build --prod` locally, then `vercel deploy --prebuilt --prod --yes`, then the explicit alias repoint to openpath-app.vercel.app.
9. **A final content-consistency audit finds what per-ticket verification cannot.** The QA pass (docs/qa-16.md) caught a persona whose stated years of experience contradicted her own CV, and three different date references for one opportunity. Each ticket was locally correct; only a cross-surface read caught it.
10. **An audit pass on an integration layer pays for itself.** The Copilot unification audit (ticket 14) found four real defects (context not loading on direct page open, dead handoffs) that per-surface testing had missed.

## 2026-07-31, RDS-976 layout, composition, and typography pass

11. **One named display step beats a one-off large heading per page.** A `.text-display` utility (one step above h1, disciplined line height, same family) let Home's greeting band and Goals' target-direction band share a real hero treatment instead of each page inventing its own oversized heading class.
12. **A quiet uppercase section label groups a dense list without adding another heading level.** Splitting Home's attention queue into "Needs a decision" and "Also worth a look" under a `.text-section-label` (the same treatment the sidebar nav groups already used) cut scanning cost on the highest-traffic surface without a new component.
13. **Don't repeat what the page header already says.** The opportunity detail page's summary band used to re-show role, company, and a breadcrumb the page header already rendered a few pixels above. Removing the duplicate line, not adding one, was the fix; the same audit found the CV detail page had never had the duplicate in the first place, so the fix was really about matching an existing better pattern.
14. **A sandboxed headless Chromium needs its shared libs pointed at explicitly.** `npx playwright install` cannot sudo in this environment; launching still works once `LD_LIBRARY_PATH` includes a prefetched lib prefix (this box keeps one at `~/.pwlibs/root/usr/lib/x86_64-linux-gnu`). Worth checking for a prebuilt lib prefix before assuming headless browser review is blocked.

## 2026-07-31, RDS-977 sources workflow (connected tools hub, synced-context inbox, source-to-object linking)

15. **A trigger that conditionally renders based on the same state its own flow is about to change will unmount itself mid-flow.** The Connect dialog's trigger lived in a parent that swapped "Connect button" for "Synced X ago" the instant `source.status` flipped to connected, which happened while the dialog's own completion step was still showing, so the whole dialog vanished before the user ever saw it. Fix: fold the branch (trigger vs. status line) into the same component that owns the Dialog's open state, so the Dialog element itself never unmounts across the status change it causes.
16. **A card that leaves the currently active filter the instant its state changes never gets to show its own inline confirmation.** Linking an inbox item moves it out of the default "Needs review" tab in the same render pass, so the five-beat pattern's inline `SaveBackConfirmation` (correct once you're looking at the "Linked" tab) was invisible to whoever triggered the action from "Needs review". A toast paired with the state change, the same pattern every other "item leaves the current list" action in this codebase already uses (dismiss a nudge, a next action, a candidate), closed the gap without touching the inline confirmation.
17. **Client-side store state resets on a real page navigation, not just a hard reload.** A headless-browser verification script that uses `page.goto()` between steps silently loses all in-session state (connected sources, links, everything), producing confusing "nothing happened" failures that look like product bugs. Once the script switched to clicking in-app `Link`s (sidebar nav, card links) instead of `page.goto()` for every step after the first load, the same checks passed correctly.

## 2026-07-31, RDS-978 copy and content-realism pass

18. **First-person AI voice survives a full polish pass because it hides in contractions, not the word "I" alone.** A grep for `\bI\b` across scripted Copilot copy misses "I'll parse it", "I've seen the role", "I don't send anything myself". Search for `I'll`, `I've`, `I'm`, `I will`, `I recommend` as their own patterns; five instances survived ticket 16's audit this way, three of them in `copilot-scripts.ts` response text a user would actually read in the panel.
19. **Check a seeded company's name against its own location field, not against the persona in general.** Three opportunities explicitly on-site or hybrid in Ho Chi Minh City (`Northwind Robotics`, `Tidal Finance`, `Brightpath Bank`) still carried pure Silicon-Valley-style names and US-scale USD salary ranges, while every remote/international opportunity in the same file read fine. The tell was the `location` field, not the company name in isolation: a company physically anchored in the persona's city needs to read like it belongs there, remote roles don't carry the same expectation.
20. **A generic feedback toast can hide behind a specific-sounding function name.** `acceptTailoringSuggestion` and `acceptWeeklyReviewSuggestion` both read `toast.success("Suggestion accepted")`, generic enough to say nothing about what changed. The fix in both cases was to have the calling component pass along data it already had in hand (`suggestion.section`, or just naming the actual effect: "Pinned to your attention queue") rather than looking anything up inside the store callback, the same pattern `linkInboxItem` already used for its own toast.

## 2026-07-31, RDS-992 app shell, navigation, and template redesign

21. **A vendored shadcn primitive can fail this repo's own lint rules.** `npx shadcn@latest add sidebar` generated `hooks/use-mobile.ts` with an effect that calls `setState` directly, which this repo's `react-hooks/set-state-in-effect` rule treats as an error, not a warning. Adding a component from the registry doesn't exempt it from the project's lint config; rewrote it on `useSyncExternalStore` instead of trusting the generated file as-is.
22. **A flex child needs `min-w-0` before `truncate` does anything.** The Opportunities Focus strip's row text used `truncate` but its ancestor `flex-1` container had no `min-w-0`, so at 1280px with both the sidebar and Copilot panel open, the flex item refused to shrink below its content's intrinsic width and the text overflowed into the Copilot panel instead of ellipsizing. `truncate` is necessary but not sufficient in a flex row; every ancestor between the truncated element and the row's flex boundary needs `min-w-0` too. Found during the UX-law review's Tesler's Law pass (system should absorb narrow-viewport complexity, not spill it onto the user) by actually opening both panels at once rather than trusting each in isolation.
23. **UX-law review checklist for this pass, one line per violation found and fixed:**
    - *Jakob's Law*: Home's attention-queue nudge rows showed their "why" line inline while `GoalCard` and `InboxItemCard` already used a click-to-expand chevron for the same kind of secondary detail. Gave nudge rows the same expand toggle so the pattern is consistent everywhere it appears.
    - *Progressive disclosure*: Sources inbox rows showed `whyItMatters` as an always-visible line on top of an already-collapsible evidence extract. Folded it into that same expand region so the row's default state is scan-only, one signal line plus one title line.
    - *Miller's Law*: Home's pipeline counts lived in a prose sentence (`buildPipelinePulse`) and a separate breakdown card below the fold, two different content shapes for the same numbers. Replaced both with one `StatTiles` strip: two headline tiles (needs a decision, interviews this week) then the five pipeline counts, chunked with a divider so it still reads as two groups, not seven flat numbers.
    - *Aesthetic-Usability / consistency*: the two existing support rails (`CvMetaRail` at w-72, `CoverageRail` at w-64) used different hardcoded widths for the same visual role. Standardized both, plus Profile's rail, to the one w-72 width the `DetailPage`/`WorkspacePage` templates now own.
    - *Tesler's Law*: every route used to hand-build its own header, padding, and max-width combination, with no shared place to own sidebar-collapse-aware layout. Centralizing that into four page templates moves the complexity into the system once instead of leaving each page to reinvent it.
    - *Proximity / Jakob*: the sidebar read as a floating aside with a visible gap from the content column, the redesign's named problem. Rebuilt on shadcn's `SidebarProvider`/`SidebarInset` pattern so the two regions form one continuous frame with no gap.
    - *Hick's Law / body-text budget*: Home's `NextActionsCard` rows carried three always-visible text lines (opportunity link, verb, rationale plus meta). Compressed to two: verb and effort/due on one line, opportunity and rationale truncated onto the next.
    - *Tesler's Law (content min-width)*: see lesson 22 above, the Focus strip's missing `min-w-0`, caught by testing sidebar-open plus Copilot-open plus a wide board view together instead of each in isolation.

## 2026-07-31, RDS-983 Roadmap (the working path turned into a guided, staged journey)

28. **`border-dashed` alone renders nothing in this codebase's Tailwind reset; it needs an explicit `border` width class too.** Styling the roadmap's "later" milestone card as `"border-dashed ring-foreground/8"` produced no visible border at all, because this project's base reset zeroes every element's border-width, and `border-dashed` only sets `border-style`. `components/track-record/candidate-card.tsx` already had the working pattern (`border-2 border-dashed border-indigo-300 ... ring-0`, an explicit width plus `ring-0` to cancel the Card component's default ring so the two don't double up); `opportunity-materials-tab.tsx`'s bare `className="border-dashed"` on a `Card` turns out to share the same latent no-op, left untouched here since it's outside this ticket's scope. Copying an existing "draft" pattern is only safe if it's one that actually renders, not just one that reads right in the source.
29. **A milestone's "resources" list will usually run taller than its "skills" and "proof" lists, so a flat 3-equal-column drill-in leaves a lopsided gap.** The first build gave Skills to move, Proof to build, and Resources one column each in a `lg:grid-cols-3` row; Resources routinely has 2 to 3 full cards while the other two groups might have as little as one short row, so the shorter columns left a wall of empty space down to the next milestone. Moved Resources to its own full-width row below a 2-column Skills/Proof row (which stay close in height to each other) and let Resources use its own `sm:grid-cols-2 lg:grid-cols-3` grid for the individual cards; this also gave each resource card enough width that its three why-lines stop wrapping into a narrow column.
30. **A milestone's roadmap progress needs to reference the specific already-true objects, not just plausible-looking ones, or the journey opens at zero everywhere.** The first pass wrote milestone 1's proof items against only forward-looking plan items (none accepted yet), the same zero-start mistake the Path Planner build's own lesson 59 already named and fixed once. Caught by actually reading the rendered "X of Y already in motion" line instead of trusting the data file: linked milestone 1's proof list back to the two `alreadyDone` growth-plan items (`plan-1-now-3`, `plan-2-now-2`) the recommended and design-lead scenarios already seed, so the journey opens already in motion for both, honestly zero only for the independent-consultant scenario whose own seed data (`readinessToday: "Not started"`) says the same thing.

## 2026-07-31, RDS-981 codebase review, cleanup, and delivery documentation

32. **A 2000-line single-file reducer splits cleanly along the app's own nav groups, not along arbitrary line counts.** `lib/store.tsx` had grown to 1993 lines across 24 tickets: one `Action` union, one switch-statement reducer, and ~90 action-creator callbacks in one `StoreProvider`. Splitting the reducer into `lib/store/reducers/*.ts` along the same domains `docs/architecture.md` section 3 already names (onboarding, opportunities, ai-signals-and-sources, cvs, direction (Goals+Planner+Roadmap+Skills, matching the DIRECTION nav group exactly), track-record-and-rewind, profile, shell) needed no new judgment calls, the boundaries were already decided by the product's own information architecture. The action-creator callbacks and `StoreProvider` component stayed in one `provider.tsx`: they all close over the same `dispatch`/`router`/`state` and are already grouped by the same domain order, splitting them further would have added indirection (cross-file `dispatch` wiring) without making anything easier to find. `lib/store/index.tsx` re-exports the same public API so none of the 66 existing `from "@/lib/store"` imports needed to change.
33. **An exported type whose only external "use" is an inferred function return type isn't dead, even though a plain grep for the identifier outside its own file finds nothing.** `ts-prune` and a naive cross-file grep disagreed on 8 candidates (`FocusItem`, `StageProgress`, `ProfileStrengthCheck`, etc.): the grep found no other file importing the type by name, but the type is real API, since the function that returns it (`getFocusItems`, `computeStageProgress`) is imported and used elsewhere, and TypeScript's checker references the type through that inference. Trust `ts-prune` (or another type-aware tool) over a plain identifier grep before deleting an exported type; the 3 genuinely dead exports found this pass (`NUDGE_FAMILY`/`NudgeFamily`, `InsightKind`, `EvidenceTag`) were confirmed by both.
34. **A shared component's own doc comment can go stale faster than the code around it.** `components/shared/object-card.tsx` claimed to be the card anatomy "shared by opportunity, CV, track record, goal, and skill cards", but only CV Versions' list actually renders it; Goals and Track Record built their own click-to-expand-in-place card family instead (a genuinely different interaction, not accidental drift, and internally consistent with itself across `GoalCard`/`TrackRecordEntryCard`/`CandidateCard`). Forcing them onto `ObjectCard` would have been an elegance-only refactor risking real behavior; fixing the comment to say what actually consumes it was the safe, honest move.
35. **A memory-constrained sandbox running multiple concurrent agent sessions can crash a headless Chromium page mid-navigation under load; retry with a fresh page/context before treating it as a product bug.** Two of thirteen route loads crashed on first attempt (`page.goto: Page crashed`) while a second, unrelated agent's own Chrome instance was running many renderer processes on the same box; both routes loaded clean (200, zero console errors) once retried on a fresh browser context. The dev server's own access log confirmed both routes had already served 200 the whole time, confirming the crash was the headless browser running out of headroom, not the app.
36. **`page.waitForLoadState("load")` after clicking a Next.js `<Link>` returns before the client-side route change lands, making an in-app nav check look broken when it isn't.** A client-side navigation never fires another `load` event, so `waitForLoadState("load")` resolves immediately against the *previous* page and `page.url()` reads stale. Swapping to a short `page.waitForTimeout()` after the click (or waiting on a piece of the next page's content) reads the real post-navigation URL correctly.

## 2026-07-31, RDS-984 product-wide UI design maturity pass

37. **A CSS Grid `CardHeader` with no explicit `grid-template-columns` blows out silently in any narrow multi-column context, and the resulting overflow gets hard-clipped mid-word by the Card's own `overflow-hidden` instead of wrapping.** Track Record's Highlights shelf (`lg:grid-cols-2 xl:grid-cols-3`) was the only place narrow enough to expose it: `CardHeader`'s single implicit grid column had no `min-width: 0`, so a card's badge row rendered at its unconstrained content width (438px measured, inside a 269px card) and visually stopped exactly at the card's right edge mid-tag. `min-w-0` on `Card` alone wasn't enough; the fix needed an explicit `grid-template-columns: minmax(0,1fr)` (and `minmax(0,1fr)_auto` for the card-action variant) on `CardHeader` itself, the CSS Grid equivalent of the flexbox `min-width: auto` blowout lessons.md #22 already named. Fixed at the primitive so every consumer benefits, not just the one shelf that happened to expose it. Diagnosed by reading actual computed bounding boxes via Playwright (`getBoundingClientRect`/`getComputedStyle`) rather than guessing from the rendered screenshot alone, since the first fix attempt (min-w-0 on Card only) looked plausible but measurably didn't change the overflow width.
38. **A card that leaves its parent's active filter the instant its own state changes can hide behind a filter it doesn't obviously belong to, not just the "wrong tab" case lessons.md #16 already named.** Home's attention queue filtered its "Needs a decision" signal list to `state === "proposed"`, one step stricter than the opportunity Overview tab's Signals section (`state !== "dismissed"`). Approving a signal on Home unmounted its `AiActionCard` in the same render, before the five-beat pattern's own save-back confirmation and Undo ever painted, so the product's highest-traffic screen gave zero feedback on its highest-value action. The two surfaces render the exact same `SignalCard` component; only the list-filtering predicate around it had drifted. Caught by actually clicking Approve and screenshotting the result, not by reading the component in isolation, since `AiActionCard` itself was correct the whole time.
39. **A `Label` with no `htmlFor` is invisible to both screen readers and `page.getByLabel()`, and it's cheap to lose track of once a form builds its own local `Field` wrapper instead of reusing one already in the codebase.** `add-opportunity-dialog.tsx`'s manual-entry tab and `profile-preferences-card.tsx`'s edit mode each hand-rolled a `Field` helper that rendered a bare `<Label>{label}</Label>` with no `htmlFor`, while `goal-form-dialog.tsx` and `entry-fields-form.tsx` already wired `htmlFor`/`id` correctly on the same kind of field. Fixed both local `Field` helpers with `useId()` plus `cloneElement` to inject a matching `id` onto the field's child control, typed as `ReactElement<{ id?: string }>` so `cloneElement` type-checks; a Select-based field harmlessly ignores the extra `id` (Radix's `Select.Root` isn't a DOM node) so the fix is safe to apply uniformly without branching per control type. Found by writing the final flow-walkthrough script: `page.getByLabel("Role title")` timed out where every other dialog's equivalent lookup worked first try.
40. **UX-law review checklist for this pass, one line per law:**
    - *Aesthetic-Usability Effect*: the `CardHeader` grid blowout (#37), the `PriorityChip` intensity drift (a lighter 50/10 tone while every other chip type had settled on 100/15), and `DesktopGuard`'s hand-rolled `text-xl` heading instead of the shared h1 token all read as small polish gaps that compound into "this wasn't finished." All three fixed.
    - *Jakob's Law*: Home's save-back confirmation gap (#38) is exactly this, one surface silently not matching the pattern users already learned from every other AI proposal in the product. `SkillLevelMeter`'s indigo dots were the same failure in miniature: indigo means "Copilot said this" everywhere else in the app, so a plain skill-level meter using it read as an AI claim it never made. Both fixed; indigo is now unused outside `components/ai/` and the handful of Copilot-attributed treatments docs/design.md section 1 names explicitly.
    - *Hick's Law*: reviewed the opportunity summary band's control row (status dropdown, priority dropdown, fit chip, Dream toggle, credibility flag, current-next-action pill) as the densest single row in the product; each control is a single independent action rather than a compounding decision, and the row already splits into two visual clusters (object-state chips left, current-action pill right via `ml-auto`). No violation found.
    - *Miller's Law*: Home's stat tiles (RDS-992 lesson 44), Rewind's 3 candidates, the Path Planner's capped alternatives, and Skills' 4-group map all still hold their caps. No violation found this pass.
    - *Proximity*: re-verified the five-beat pattern's evidence chip sits directly under its own signal line and controls sit directly below their own proposed-action block on every `AiActionCard` consumer (Home, Opportunity Signals). No violation found.
    - *Progressive Disclosure*: re-verified evidence extracts, "Why this reading," and the Alternatives comparison's expandable rows all still default collapsed. No violation found.
    - *Serial Position*: Home's "Needs a decision" leads "Also worth a look," which leads "Next actions"; Roadmap's "Do this today" still renders first and stays sticky. No violation found.

## 2026-08-01, RDS-985 opportunity comparison and decision workspace

## 2026-08-01, RDS-991 public landing page (product storytelling, showcase, motion)

69. **A "custom hook returns an object containing a ref" pattern trips the newer `react-hooks/refs` lint rule even when nothing ever reads `.current` during render.** A `useParallax()` hook returning `{ ref, style }` (so a showcase frame could do `<div ref={parallax.ref} style={parallax.style}>`) failed lint with "Cannot access ref value during render" on both property accesses, even though neither is `.current`. The rule's static analysis appears to taint the whole returned object once it contains a value derived from `useRef`, and flags any later property access on it. The fix: keep `useRef` in the consuming component itself (`const frameRef = useRef<HTMLDivElement>(null)`) and pass that ref into the hook as a parameter instead of getting one back out of it (`useParallax(frameRef)` returning just a plain number). A custom hook that only *consumes* a caller-owned ref, rather than creating and returning one bundled with other data, is the pattern this rule can verify as safe.
70. **A decorative composition rendering real, live product components needs `inert`, not just `pointer-events-none`.** The four showcase frames render actual `AiActionCard`/`OpportunityBoardView`/`MilestoneNode` instances with real buttons, links, and form controls inside them; `pointer-events-none` alone stops mouse interaction but leaves every one of those controls keyboard-focusable and present in the accessibility tree, so a keyboard or screen-reader visitor would tab into a decorative five-beat card's Approve button that does nothing. `inert` (a real HTML/React 19 attribute, not just a class) removes the whole subtree from both focus order and the accessibility tree in one attribute, which is what `components/marketing/browser-frame.tsx` uses on its cropped viewport wrapper. The landing's own sticky CTA bar needed the identical fix for the opposite reason: it stays mounted (for its exit transition) even while visually hidden above the viewport via `-translate-y-full`, and a plain `pointer-events-none` visually-hidden-but-still-focusable link there is exactly the kind of thing `getByRole` locators (and real keyboard users) will still find, which is how this was caught, a headless-browser CTA click hung retrying against an off-screen `<a>` Playwright still considered "visible."
71. **A chip row that fits comfortably at every desktop width can still overflow a 390px viewport, and the overflow shows up as a page-wide `scrollWidth` mismatch, not a visibly broken chip.** Three `ConfidenceChip`s in a plain `flex items-center justify-center gap-2` row (the AI-difference section's "High confidence / Medium confidence / Low confidence" demonstration) fit at 1440, 1024, and 768 but ran 10px past 390px's content width, the exact size of the page's own horizontal-overflow measurement. Nothing about the row's own rendering looked clipped or broken in a full-page screenshot at that width; the fix (`flex-wrap` added to let the row become two lines on the narrowest viewport) is trivial once found, but finding it needed a programmatic `document.documentElement.scrollWidth - clientWidth` check at each of the four required widths, not a visual scan, and then a second pass that only counts elements *not* already clipped by an ancestor's own `overflow-hidden` (the showcase frames' real, scaled-up internal content routinely reports off-screen bounding boxes that never actually reach the page, and a naive "any element wider than the viewport" scan flags dozens of false positives from inside those frames).
72. **A `BrowserFrame`'s skeleton-to-real-content height reservation needs to be measured, not guessed, or a lazy-mounted showcase visibly shifts the page under a scrolling visitor.** `components/marketing/lazy-mount.tsx` reserves `cropHeight + 45` px for each showcase's `ShowcaseSkeleton` before it lazy-mounts the real `BrowserFrame`; the `+45` (the chrome bar's height) was a first-pass estimate, confirmed correct only by measuring the 5 real rendered frames' actual heights afterward (all landed within 0.5px of the reservation). Bundle-discipline lazy-mounting done well recovers exactly the initial-load win it's meant to; done with a guessed placeholder height it trades that win for a CLS regression on every scroll.
73. **The landing's client-side "Open OpenPath" CTA re-reads the store's `onboarded` flag fresh on every mount, so a hard page reload of "/" always re-offers onboarding even in the same browser tab that finished it minutes earlier.** This is not a landing-page bug: the whole prototype has no persistence and resets state on any real reload by design (docs/architecture.md section 2), and the CTA's `state.onboarded ? "/home" : "/onboarding"` check is the exact same one the old `app/page.tsx` root redirect ran before this ticket. A same-session, no-reload verification (skip onboarding, confirm landing on `/home`) is the correct test; a `page.goto("/")` between steps produces a "failure" that is really lessons.md #17's class of mistake recurring at the landing-page layer.
