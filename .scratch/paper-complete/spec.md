# Complete My Paper

Product locks: [`docs/paper.md`](../../docs/paper.md). Visual locks: [`../paper-redesign/spec.md`](../paper-redesign/spec.md). Nouns: [`CONTEXT.md`](../../CONTEXT.md). Build order: [map](map.md).

This spec is for an agent that writes code. It does not reopen Paper, Drive, Docs, CV, letter, or Proof.

## Problem Statement

On deadline night I need a CV I can send. My Paper is supposed to be one room: I pick a paper, then I write on it. Today the list and the opened paper feel like two apps. The CV still thinks in a form. An uploaded file does not honestly start a built CV. A Proof is a notes form, not a space I can publish as a considered page. The personal link still smells like a calendar of days I used the app.

I already decided what this should be. I do not want another grill. I want the app to match those answers.

## Solution

My Paper stays Drive, then Docs. I pick from a sheet-edge stack. I write on the output — the A4, the letter or email page, or the Proof space. An uploaded file stays a file; a built CV can start from it without pretending we read it. I Arrange a draft of the real public page, then Publish. My personal link is a sentence and a span record of published work, not a streak grid.

## Implementation Decisions

- Callers still see one Paper with types CV, letter, and Proof. Uploads stay a sibling list on AppState, not a fourth type. (ADR 0003)
- All mutations go through the existing `paper.*` actions on applyAction. Do not add a second write path. The Coach validates; the tab applies.
- Drive and Docs are two modes of one My Paper shell. The sticky band stays mounted. The body is the stack, a Drive-mode chooser, or the opened paper. Do not keep two full page trees.
- Opening a built paper is a shared-element transition (name → title, slab → sheet) using the already-locked motion tokens. No origin skips travel.
- Creating a CV from the unmade object or New opens the eight-situation gallery as a Drive mode. Creating a CV from an upload write door skips the gallery and uses a blank CV with a plain starter structure and `fromProfile` false.
- Changing situation on an existing CV uses the existing theme action. Typed entries stay. Photo visibility follows whether the situation has a photo area.
- Changing letter situation uses the letter-situation action: unused scaffold is replaced; typed body stays. Speculative uses an email-shaped page; the other three use a letter page.
- Proof notes remain newest-first in the space. Arrange stores a why and an ordered list of note ids on the Proof. Publish snapshots that selection. The public page and the Arrange draft share one layout.
- Public pages read published snapshots, not live AppState. Span placement is derived from role · dates, or Publish day when dates are missing. Do not feed the mark from logging days.
- New proof kinds (photo, file, link) extend the existing Proof model and `paper.*` actions. Do not invent a second artefact. Do not fake extract or inbox scan.
- Unpublish removes the public URL and leaves the space. Republish is Arrange plus Publish again.
- Completeness stays a function of the opened CV. It never appears on a Drive row.
- Copy stays mentor voice: sentence case, second person, no exclamation marks. Screen name remains My Paper.

## Testing Decisions

Good tests assert external behaviour through the highest seam: apply an action, read AppState (or a snapshot helper). They do not assert class names, pixel values, or component trees.

**Seam 1 — applyAction (`paper.*`).** Prefer this for every create, rename, theme, section, entry, paragraph, note, proof meta, letter situation, publish stamp, and upload. Prior art: existing paper action tests (create, entries, notes newest-first, publish slug, upload is not a paper, letter paragraphs, theme leaves content).

**Seam 2 — snapshot and span helpers.** Prefer this for Arrange filtering, why, publish-day ticks, year grouping, and “no dates → tick.” Prior art: share helper tests and span helper tests. Do not use a day-grid helper as the personal-link assertion.

Do not add a third seam. Do not test Drive/Docs chrome through the DOM unless a ticket cannot be proven at these two seams (then one walkthrough in the ticket Verify, not a new harness).

Check: if these two seams are wrong, say so before implementation starts. The expectation is they match — they are the seams the app already uses.

## Out of Scope

- Coach thumbnail inheriting Docs (later).
